# Проверка трассируемости спецификации

`check_traceability.py` проверяет, что разделы спецификации согласованы между собой: все ссылки ведут на существующие ID, у каждого требования есть проверка, у каждого метода API есть причина существовать.

## Требования

Python 3.9 или новее. Сторонние библиотеки не нужны, только стандартная библиотека.

## Запуск

Из корня репозитория:

```bash
python3 tools/check_traceability.py                    # проверить example/
python3 tools/check_traceability.py template           # проверить пустой шаблон
python3 tools/check_traceability.py specs/my-feature   # проверить свою спецификацию
```

Аргумент — путь к папке с разделами. Если его нет, проверяется `example/`.

Код возврата:
- `0` — ошибок нет (предупреждения могут быть);
- `1` — найдены ошибки.

Код возврата позволяет запускать скрипт в CI: шаг с ошибкой «покраснеет» так же, как упавший тест.

## Как читать вывод

```text
Спецификация: example

| Что проверяется             | Всего | Покрыто | Не покрыто |
|-----------------------------|-------|---------|------------|
| ФТ с критерием приёмки      | 24    | 24      | 0          |
| Бизнес-правила с критерием  | 10    | 10      | 0          |
| НФТ с проверкой             | 16    | 16      | 0          |
| Методы API с ФТ             | 15    | 15      | 0          |
| Переходы статусов в матрице | 8     | 8       | 0          |

Определено: 24 ФТ, 16 НФТ, 10 правил, 51 критериев, 15 методов API, 21 кодов ошибок, 8 переходов

Ошибок не найдено.
```

- **Сводка покрытия** — сколько элементов каждого вида и сколько из них покрыто. Её можно вставить в раздел 13.6.
- **Определено** — сколько ID скрипт нашёл в таблицах определений. Если число меньше ожидаемого, скорее всего, строка таблицы оформлена не так, как ждёт скрипт (см. «Как скрипт находит ID»).
- **ПРЕДУПРЕЖДЕНИЕ** — подозрительное место, которое не ломает проверку. Например, критерий ссылается на требование, но не указан в матрице.
- **ОШИБКА** — расхождение, которое нужно исправить.

## Что означают ошибки и как их исправить

| Сообщение | Что случилось | Что делать |
|-----------|---------------|------------|
| `Ссылка на неопределённый ID: FR-99` | Где-то в тексте упомянут FR-99, но в таблице ФТ раздела 3 его нет | Найти место ссылки (`grep -rn "FR-99" <папка>`) и исправить опечатку, либо добавить требование в раздел 3 |
| `Код ошибки не описан в каталоге 5.4: OUT_OF_STOK` | В тексте упомянут код ошибки, которого нет в каталоге | Исправить опечатку или добавить код в каталог раздела 5.4 |
| `ФТ FR-05 не покрыто ни одним критерием приёмки` | Ни один критерий в разделе 12 не ссылается на FR-05 в колонке «Связь» | Написать критерий приёмки или добавить FR-05 в колонку «Связь» существующего |
| `Бизнес-правило BR-04 не покрыто ни одним критерием приёмки` | То же для правила | Добавить критерий, который проверяет нарушение правила |
| `НФТ NFR-03 не покрыто ни одним критерием приёмки` | То же для НФТ | Добавить строку в таблицу приёмки НФТ (AC-Nxx) |
| `FR-06 отсутствует в матрице 13.2` | Требование есть в разделе 3, но не в матрице | Добавить строку в матрицу 13.2 |
| `В матрице у FR-06 нет критериев приёмки` | Строка в матрице есть, но последняя колонка пустая | Указать критерии в последней колонке |
| `Метод API E2 не связан ни с одним ФТ в 13.5` | Метод описан в разделе 5, но в обратной трассировке у него нет требования | Добавить строку в 13.5. Если требования действительно нет — возможно, метод лишний |
| `AC-07 не ссылается ни на одно требование или правило` | Колонка «Связь» критерия пустая или без ID | Указать, что проверяет критерий |

## Как скрипт находит ID

Скрипт не понимает Markdown целиком, он ищет строки таблиц. ID считается **определённым**, если он стоит в первой колонке таблицы в своём разделе:

| ID | Раздел (файл) | Пример строки |
|----|---------------|---------------|
| `BG-xx` | `01_*.md` | `\| BG-01 \| Увеличить продажи \| …` |
| `FR-xx`, `NFR-xx` | `03_*.md` | `\| FR-01 \| Покупатель может… \| …` |
| `UCx`, `UCx.y` | `04_*.md` | `\| UC2.1 \| Добавление товара \| …` |
| `AF-x` | `04.1_*.md` | `\| AF-1 \| 10 \| Срок оплаты истёк \| …` |
| `Ax`, `Wx`, `Ex` | `05_*.md` | `\| A1 \| Добавление товара \| POST \| …` |
| `T-xx` | `08_*.md` | `\| T-01 \| — \| created \| …` |
| `BR-xx` | `10_*.md` | `\| BR-01 \| Лимит 10 шт. \| …` |
| `AC-xx`, `AC-Nxx` | `12_*.md` | `\| AC-01 \| FR-01, BR-01 \| Дано… \| …` |
| Коды ошибок | `05_*.md` | `` \| 409 \| `OUT_OF_STOCK` \| … `` |

**Ссылкой** считается любое упоминание ID в тексте любого раздела, в том числе внутри таблиц и диаграмм в блоках кода. Коды ошибок считаются ссылками, только если записаны в обратных кавычках: `` `OUT_OF_STOCK` ``.

Специальные колонки, которые читает скрипт:
- **раздел 12, вторая колонка («Связь»)** — что проверяет критерий;
- **раздел 13.2, последняя колонка** — критерии для каждого ФТ;
- **раздел 13.5** — строки, начинающиеся с номера метода API.

`README.md` в папке спецификации не проверяется: в нём ID приводятся как примеры.

## Как устроен скрипт

1. `read()` читает файл раздела по префиксу номера (`03`, `04.1`, `13`).
2. `table_rows()` возвращает строки таблиц, у которых первая ячейка подходит под шаблон ID. Из них собираются множества определённых ID.
3. Регулярное выражение `ID_RE` находит все упоминания ID во всех разделах. Разница «упомянуто минус определено» — ошибки первого типа.
4. По колонке «Связь» раздела 12 строится словарь «критерий → что он проверяет». По нему считается покрытие требований и правил.
5. Таблицы раздела 13 сверяются с определениями.
6. Печатается сводка, предупреждения и ошибки; возвращается код 0 или 1.

## Как добавить новый тип ID

Например, чтобы проверять ссылки на события аудита `AUD-xx` из раздела 11:

1. Добавить префикс в регулярное выражение `ID_RE`:
   ```python
   ID_RE = re.compile(r"\b(?:FR|NFR|BR|BG|T|AF|AUD)-\d+\b|…")
   ```
2. Прочитать раздел и собрать определения в `main()`:
   ```python
   s11 = read("11")
   audit = set(table_rows(s11, r"AUD-\d+"))
   ```
3. Добавить новое множество в `defined`:
   ```python
   defined = bg | fr | … | audit
   ```
4. Проверить на копии спецификации, что опечатка в новом ID действительно ловится.

## Ограничения

- Скрипт проверяет связи, а не смысл. Что критерий проверяет именно то, что написано в требовании, может оценить только человек.
- Диапазоны вида `FR-03…FR-06` не раскрываются: проверяются только концы диапазона.
- Номера методов API ограничены двумя цифрами (`A1`…`A99`), чтобы не путать их с примерами данных вроде `A001`.
- Если строка таблицы оформлена нестандартно (ID не в первой колонке, лишний текст в ячейке с ID), скрипт её не увидит. Число в строке «Определено» помогает это заметить.

## Использование в CI

Минимальный шаг для GitHub Actions:

```yaml
- name: Проверка трассируемости
  run: |
    python3 tools/check_traceability.py example
    python3 tools/check_traceability.py template
```

Если любая из команд вернёт 1, шаг и весь workflow завершатся с ошибкой.
