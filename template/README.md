# Шаблон описания фичи

Пустой шаблон из 13 разделов с подсказками по заполнению. Заполненный пример каждого раздела — в папке [`example/`](../example/), ссылка на него есть в начале каждого файла.

## Как начать

1. Скопируйте папку `template/` в новую, например `specs/my-feature/`.
2. Заполняйте разделы в порядке ниже, заменяя текст *курсивом* на свой.
3. Удаляйте подразделы, которые не нужны вашей фиче (например, интерфейс, если его нет), но не удаляйте разделы целиком: лучше написать «не применимо» и почему.
4. После каждого раздела запускайте проверку:
   ```bash
   python3 tools/check_traceability.py specs/my-feature
   ```

## Порядок заполнения

Разделы пронумерованы в порядке чтения, но заполнять удобнее итерациями:

| Итерация | Разделы | Результат |
|----------|---------|-----------|
| 1. Контекст | 01 → 02 | Понятно, что и зачем делаем |
| 2. Поведение | 04 → 4.1 → 03 | Кто что делает, по шагам, и какие требования из этого следуют |
| 3. Устройство | 06 → 05 → 07 | Из чего состоит решение, как компоненты общаются, какие данные хранятся |
| 4. Правила | 08 → 10 → 09 → 11 | Статусы, бизнес-правила, доступы, аудит |
| 5. Проверка | 12 → 13 | Критерии приёмки и матрица, которая показывает пробелы |

После итерации 5 почти всегда приходится вернуться к 4.1 и 03: матрица находит шаги и требования, которые были пропущены.

## Соглашения об идентификаторах

| Префикс | Что обозначает | Где определяется | Пример |
|---------|----------------|------------------|--------|
| BG-xx | Бизнес-цель | 01 | BG-01 |
| FR-xx | Функциональное требование | 03 | FR-01 |
| NFR-xx | Нефункциональное требование | 03 | NFR-01 |
| UCx, UCx.y | Вариант использования | 04 | UC1, UC1.1 |
| AF-x | Альтернативный путь сценария | 4.1 | AF-1 |
| Ax, Wx, Ex | Метод API: публичный, входящее уведомление, исходящий вызов | 05 | A1, W1, E1 |
| T-xx | Переход статуса | 08 | T-01 |
| BR-xx | Бизнес-правило | 10 | BR-01 |
| AUD-xx, EVT-xx | Событие аудита, системное событие | 11 | AUD-01 |
| AC-xx, AC-Nxx | Критерий приёмки функциональный и нефункциональный | 12 | AC-01, AC-N01 |

ID определяется в первой колонке таблицы своего раздела, во всех остальных местах на него ссылаются. ID не переиспользуются: если требование удалено, его номер не присваивается новому.

В шаблоне уже есть минимальный связанный набор (BG-01 → FR-01 → UC1 → A1 → BR-01 → T-01 → AC-01), поэтому проверка проходит на пустом шаблоне. Замените эти строки своими и добавляйте новые.

## Что проверяет скрипт

- Все ID, на которые есть ссылки, определены в своих разделах.
- Все коды ошибок, упомянутые в тексте, есть в каталоге раздела 5.4.
- У каждого ФТ, бизнес-правила и НФТ есть хотя бы один критерий приёмки.
- Каждое ФТ есть в матрице 13.2, каждый метод API — в 13.5.
- Каждый критерий приёмки ссылается хотя бы на одно требование.

Чего скрипт не проверяет: смысл. Он скажет, что у FR-07 есть критерий, но не скажет, что критерий проверяет не то. Для этого нужно ревью.
