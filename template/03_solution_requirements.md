# 3. Требования к решению

> [!NOTE]
> **Зачем раздел:** перевести бизнес-требования в проверяемые требования к системе. По каждому ФТ потом пишется критерий приёмки (раздел 12), а матрица (раздел 13) проверяет, что ни одно требование не потерялось.
> **Входные данные:** разделы 1, 2 и варианты использования из раздела 4.
> **Пример заполнения:** [example/03_solution_requirements.md](../example/03_solution_requirements.md)

## 3.1 Границы решения

**Входит в решение:** *перечень функций*

**Не входит в решение:** *что осознанно не делаем в этой версии и почему*

**Допущения:** *что считаем верным без проверки (например, «пользователь авторизован», «остатки обновляются раз в 5 минут»)*

## 3.2 Функциональные требования (ФТ)

| ID | Требование | UC | Бизнес-правила | Приоритет |
|----|-----------|----|----------------|-----------|
| FR-01 | *Пользователь может… / Система должна… — одно действие, одна проверяемая формулировка* | UC1 | BR-01 | *Must / Should / Could / Won't* |

> [!TIP]
> Хорошее ФТ отвечает на вопрос «что делает система» и проверяемо. Плохо: «удобная корзина». Хорошо: «при повторном добавлении товара система увеличивает количество в существующей позиции». Группируйте ФТ по функциональным блокам подзаголовками.

## 3.3 Нефункциональные требования (НФТ)

| ID | Категория | Требование | Как проверяется |
|----|-----------|-----------|-----------------|
| NFR-01 | *Производительность / нагрузка / доступность / надёжность / безопасность / персональные данные / хранение / масштабируемость / наблюдаемость / совместимость / сопровождаемость* | *Число, единица измерения и условия: «p95 ≤ 300 мс при 1 000 одновременных пользователей»* | *Нагрузочный тест, мониторинг, ревью…* |

> [!TIP]
> Пройдитесь по всем категориям из колонки «Категория» и для каждой решите: есть требование или осознанно нет. Чаще всего забывают надёжность при сбоях внешних систем, идемпотентность и сроки хранения данных.

## 3.4 Открытые вопросы

| № | Вопрос | Кому задан | Статус |
|---|--------|-----------|--------|
| 1 | *Что не удалось выяснить* | *У кого выясняем* | *Открыт / Закрыт: ответ* |

---

### Типичные ошибки

- Несколько требований в одной строке — их невозможно проверить по отдельности.
- НФТ без чисел: «система должна работать быстро».
- Требование из «Не входит в решение» всё равно появляется в списке ФТ.

### Раздел готов, когда

- [ ] У каждого ФТ есть ID, ссылка на UC и приоритет
- [ ] У каждого НФТ есть число и способ проверки
- [ ] Границы решения согласованы с заказчиком
- [ ] Каждое ФТ покрыто критерием приёмки в разделе 12 (проверяет `tools/check_traceability.py`)
