# 11. Аудит действий, системные события и логирование

> [!NOTE]
> Пример заполнения раздела для решения «Онлайн-заказ в магазине смартфонов».
> Реализует FR-23, NFR-11, NFR-12 и NFR-14 из [раздела 3](03_solution_requirements.md).

## 11.1 Три вида записей

Их часто смешивают, но у них разные читатели, сроки хранения и требования.

| Вид | Отвечает на вопрос | Кто читает | Где хранится | Срок хранения |
|-----|-------------------|-----------|--------------|---------------|
| **Журнал аудита** | Кто, что и когда сделал с данными | Администратор, служба безопасности, разбор спорных ситуаций | Таблица `audit_log` в `cmsDB`, только добавление записей | 1 год (NFR-12) |
| **Системные события** | Что произошло с бизнес-объектом | Другие процессы, аналитика, мониторинг | Таблица `order_status_history` + метрики | Вместе с заказом, 5 лет |
| **Технические логи** | Как отработал запрос и где сломался | Разработчики, поддержка | Централизованное хранилище логов (например, ELK) | 90 дней (NFR-12) |

## 11.2 Журнал аудита

### События аудита

| ID | Событие | Инициатор | Объект | Что записать в `changes` |
|----|---------|-----------|--------|--------------------------|
| AUD-01 | Создан заказ | `customer` | order | Сумма, количество позиций |
| AUD-02 | Изменены данные покупателя в заказе | `customer` | order | Какие поля изменены (значения замаскированы) |
| AUD-03 | Изменён профиль | `customer` | user | Какие поля изменены (значения замаскированы) |
| AUD-04 | Начата оплата | `customer` | payment | Способ оплаты, сумма |
| AUD-05 | Изменён статус заказа | любой | order | Старый и новый статус, ID перехода (T-xx) |
| AUD-06 | Заказ отменён | `customer` / `operator` / `system` | order | Причина |
| AUD-07 | Получено уведомление с неверной подписью | `svc_payment` / `svc_delivery` | webhook | IP-адрес источника, тип уведомления |
| AUD-08 | Оператор открыл контакты покупателя | `operator` | order | ID заказа |
| AUD-09 | Оператор повторно передал заказ в доставку | `operator` | order | Номер попытки |
| AUD-10 | Оператор снял флаг `needs_attention` | `operator` | order | Комментарий |
| AUD-11 | Назначена или снята роль | `admin` | user | Роль, кому |
| AUD-12 | Отказ в доступе (403) | любой | любой | Метод, роль |

> [!TIP]
> Действия с корзиной (добавить, удалить, изменить количество) в журнал аудита не пишутся: они не меняют обязательств магазина и создают слишком много записей. Для аналитики поведения в корзине используются продуктовые события, а не аудит.

### Структура записи аудита (`audit_log`)

| Поле | Тип | Пример | Описание |
|------|-----|--------|----------|
| id | bigint | `884213` | Идентификатор записи |
| event_code | varchar(10) | `AUD-05` | Код события из таблицы выше |
| actor_type | varchar(20) | `customer` | Роль инициатора (раздел 9) |
| actor_id | varchar(20) | `U001` | Кто сделал. Для системных ролей — имя сервиса |
| object_type | varchar(20) | `order` | Тип объекта |
| object_id | varchar(64) | `O001` | Идентификатор объекта |
| changes | jsonb | `{"from": "awaiting_payment", "to": "paid", "transition": "T-04"}` | Что изменилось |
| ip_address | inet | `203.0.113.17` | IP инициатора (для людей и внешних систем) |
| trace_id | varchar(32) | `7f3c9a2e5b1d4f08` | Связь с техническими логами |
| created_at | timestamptz | `2026-06-15T12:49:40+03:00` | Время события |

Требования к журналу:
- записи только добавляются: у сервиса нет прав на `UPDATE` и `DELETE` для `audit_log`;
- запись аудита создаётся в той же транзакции, что и изменение данных: если изменение откатилось, записи аудита тоже нет;
- персональные данные в `changes` маскируются по правилам 11.5.

## 11.3 Системные события

| ID | Событие | Когда возникает | Где фиксируется | Кто использует |
|----|---------|-----------------|-----------------|----------------|
| EVT-01 | `order.created` | T-01 | `order_status_history`, метрика `orders_created_total` | Аналитика конверсии |
| EVT-02 | `order.payment_started` | T-02 | `order_status_history` | Аналитика воронки оплаты |
| EVT-03 | `order.paid` | T-04 | `order_status_history`, метрика `orders_paid_total` | Передача в доставку, финансы |
| EVT-04 | `order.payment_failed` | T-03 | Метрика `payments_failed_total` с причиной | Мониторинг платёжного шлюза |
| EVT-05 | `order.cancelled` | T-05, T-06 | `order_status_history`, метрика с причиной | Аналитика отказов |
| EVT-06 | `order.in_delivery` | T-07 | `order_status_history` | Покупатель видит статус |
| EVT-07 | `order.delivered` | T-08 | `order_status_history` | Аналитика сроков доставки |
| EVT-08 | `order.needs_attention` | Флаг выставлен | Метрика `orders_needs_attention` | Оповещение оператору |

## 11.4 Технические логи

### Уровни логирования

| Уровень | Что пишется | Примеры |
|---------|-------------|---------|
| `ERROR` | Ошибки, после которых запрос не выполнен по вине системы | Ответы 5xx, исключения, недоступность БД |
| `WARN` | Нештатные ситуации, которые система обработала | Повтор вызова E2, уведомление по неизвестному платежу, 409 `INVALID_STATUS_TRANSITION` от W2 |
| `INFO` | Ключевые шаги бизнес-сценария | Заказ создан, платёж создан, отправление создано |
| `DEBUG` | Подробности для разработки | Тела запросов к внешним системам (с маскированием). В production отключён |

### Обязательные поля каждой записи лога

`timestamp`, `level`, `service`, `traceId`, `userId` (если есть), `method`, `path`, `status`, `durationMs`, `message`.

Пример:

```json
{
  "timestamp": "2026-06-15T12:48:12.341+03:00",
  "level": "INFO",
  "service": "cmsService",
  "traceId": "7f3c9a2e5b1d4f08",
  "userId": "U001",
  "method": "POST",
  "path": "/api/v1/orders/O001/payment",
  "status": 201,
  "durationMs": 842,
  "message": "Payment created",
  "orderId": "O001",
  "paymentId": "P001",
  "contactPhone": "+7812*****00"
}
```

### Сквозной `traceId` (NFR-14)

1. `guiGateway` создаёт `traceId` для каждого входящего запроса или берёт его из заголовка `X-Trace-Id`, если тот уже есть.
2. `traceId` передаётся во все внутренние вызовы в заголовке `X-Trace-Id` и пишется в каждую запись лога и аудита.
3. При ошибке `traceId` возвращается клиенту в теле ответа ([раздел 5.4](05_integration_api.md#формат-ошибки)), и поддержка находит по нему всю цепочку вызовов.

## 11.5 Маскирование персональных данных (NFR-11)

| Данные | Как маскируется | Пример |
|--------|-----------------|--------|
| Телефон | Видны код страны, первые 3 и последние 2 цифры | `+7812*****00` |
| Email | Видны первая буква имени и домен | `e******@example.com` |
| Имя | Первая буква | `Д.` |
| Адрес | Только город | `Санкт-Петербург, ***` |
| Токены, ключи, подписи | Не пишутся совсем | — |
| Данные карт | В систему не попадают (NFR-09) | — |

> [!TIP]
> Маскирование делается в одном месте — в общей библиотеке логирования, а не в каждом вызове. Иначе рано или поздно кто-то забудет замаскировать новое поле.

## 11.6 Мониторинг и оповещения

| Метрика | Порог оповещения | Кому | Связь с требованием |
|---------|------------------|------|---------------------|
| Доля ответов 5xx по API заказа | > 1% за 5 минут | Дежурный разработчик | NFR-04 |
| p95 времени ответа A1–A11 | > 300 мс за 10 минут | Дежурный разработчик | NFR-01 |
| Ошибки E1 (платёжный шлюз) | > 5% за 5 минут | Дежурный + менеджер платёжного направления | NFR-07 |
| Заказы с `needs_attention` | > 0 дольше 30 минут | Оператор магазина | NFR-07 |
| Уведомления с неверной подписью | > 10 за час | Служба безопасности | NFR-10 |
| Доля отменённых по сроку заказов | > 30% за день | Владелец продукта | BR-05 |
