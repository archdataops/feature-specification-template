# feature-specification-template

Шаблон для описания фичи «от бизнес-требований до API, данных и критериев приёмки» и полностью заполненный пример: онлайн-заказ в магазине смартфонов.

Шаблон собран по опыту работы с описанием фич в нескольких крупных компаниях (банки, ритейл, телеком) и обобщён: все формулировки и пример написаны с нуля и не повторяют внутренние стандарты конкретных компаний.

## Как связаны разделы

Каждый следующий раздел выводится из предыдущих и ссылается на них по ID. Это позволяет проверить, что ни одно требование не потерялось по пути от бизнес-цели до теста.

```text
01 Цели и сущности (BG-xx)
 └─ 02 Бизнес-требования
     └─ 03 ФТ и НФТ (FR-xx, NFR-xx)
         └─ 04 Варианты использования (UCx)
             └─ 04.1 Сценарий по шагам
                 └─ 05 Интеграция и API (A1…, W1…, E1…) + каталог ошибок
                     ├─ 06 Компоненты
                     └─ 07 Структура данных
                         ├─ 08 Статусная модель (T-xx)
                         ├─ 09 Роли и матрица доступа
                         ├─ 10 Бизнес-правила (BR-xx)
                         ├─ 11 Аудит и логирование (AUD-xx)
                         ├─ 12 Критерии приёмки (AC-xx)
                         └─ 13 Матрица трассируемости
```

## Где применять

- **Описание новой фичи** — от бизнес-целей до критериев приёмки, чтобы разработка, тестирование и заказчик читали один документ.
- **Разбор унаследованной системы с ИИ-агентом.** Шаблон задаёт агенту структуру: какие сущности, API, статусы, правила и роли нужно восстановить по коду и документации. Скрипт проверки потом показывает, где агент оставил пробелы или сослался на то, чего нет.

## API и Swagger UI

Публичный API примера описан в [`api/openapi.yaml`](api/openapi.yaml) (OpenAPI 3.0). Номера методов в поле `x-spec-id` совпадают с разделом 5 и матрицей трассируемости, а скрипт проверки сверяет спецификацию с документом.

Посмотреть документацию API:
- **на GitHub Pages** — когда репозиторий публичный, Swagger UI публикуется автоматически (настройка ниже);
- **локально** — из корня репозитория выполнить `python3 -m http.server 8000` и открыть `http://localhost:8000/docs/`;
- **в VS Code** — расширение «OpenAPI (Swagger) Editor», открыть `api/openapi.yaml`.

<details>
<summary>Как включить публикацию на GitHub Pages</summary>

1. Сделать репозиторий публичным (**Settings → General → Danger Zone → Change visibility**). Для приватных репозиториев GitHub Pages доступен только на платном тарифе.
2. **Settings → Pages → Build and deployment → Source:** выбрать **GitHub Actions**.
3. **Actions → Spec checks → Run workflow** (или любой пуш в `main`).

Через пару минут Swagger UI будет доступен по адресу `https://<аккаунт>.github.io/<репозиторий>/`. Ссылка также появится в **Settings → Pages** и в правой колонке репозитория (**Deployments**).

Что делать после перевода репозитория в приват и обратно, как проверить состояние и что делать при ошибках — в [docs/publishing.md](docs/publishing.md). Короткий путь: `tools/publish_pages.sh`.

</details>

## Непрерывная проверка (GitHub Actions)

Workflow [`.github/workflows/spec-checks.yml`](.github/workflows/spec-checks.yml) запускается при каждом пуше и pull request:

| Шаг | Что проверяет |
|-----|---------------|
| Трассируемость примера | Все ID и коды ошибок согласованы, у требований есть проверки, методы раздела 5 совпадают с `openapi.yaml` |
| Трассируемость шаблона | Пустой шаблон остаётся согласованным |
| Линтер OpenAPI (Redocly) | Спецификация валидна, примеры соответствуют схемам |
| Синтаксис PlantUML | Все диаграммы в `diagrams/` собираются без ошибок |
| Публикация Swagger UI | Только из `main` и только для публичного репозитория |

## Автоматическая проверка согласованности

**Зачем.** Спецификация держится на перекрёстных ссылках: требование ссылается на бизнес-правило, критерий приёмки — на требование, матрица — на всё сразу. Когда документ меняется (правило переименовали, требование удалили, добавили метод API и забыли про тест), ссылки расходятся, и вручную это почти невозможно заметить. Скрипт [`tools/check_traceability.py`](tools/check_traceability.py) находит такие места автоматически — так же, как тесты находят ошибки в коде.

**Что он проверяет:**
- каждый ID, на который есть ссылка (FR, BR, AC, UC, методы API и другие), определён в своём разделе;
- каждый код ошибки, упомянутый в тексте, есть в каталоге ошибок;
- у каждого функционального и нефункционального требования и бизнес-правила есть хотя бы один критерий приёмки;
- каждое требование есть в матрице трассируемости, у каждого метода API есть требование, ради которого он существует.

**Чего он не проверяет:** смысл. Скрипт убедится, что у требования есть критерий приёмки, но не поймёт, что критерий проверяет не то. Для этого нужно ревью.

```bash
python3 tools/check_traceability.py                                  # проверить пример
python3 tools/check_traceability.py template                         # проверить шаблон или свою спецификацию
python3 tools/check_traceability.py example --openapi api/openapi.yaml   # плюс сверка с OpenAPI
```

Как скрипт устроен, как читать его вывод и исправлять ошибки — в [tools/README.md](tools/README.md).

Результат для примера:

```text
| Что проверяется             | Всего | Покрыто | Не покрыто |
|-----------------------------|-------|---------|------------|
| ФТ с критерием приёмки      | 24    | 24      | 0          |
| Бизнес-правила с критерием  | 10    | 10      | 0          |
| НФТ с проверкой             | 16    | 16      | 0          |
| Методы API с ФТ             | 15    | 15      | 0          |
| Переходы статусов в матрице | 8     | 8       | 0          |
```

Скрипт использует только стандартную библиотеку Python и завершается с кодом 1 при ошибках, поэтому подходит для CI.

## Структура репозитория

```text
example/    заполненный пример (разделы 01–13)
template/   пустой шаблон с подсказками и минимальным набором связанных ID
diagrams/   исходники PlantUML (.puml) и отрендеренные SVG
tools/      скрипт проверки трассируемости
api/        спецификация OpenAPI
docs/       страница Swagger UI для GitHub Pages
assets/     макеты интерфейса и иллюстрации
.github/    workflow проверок и публикации
redocly.yaml  настройки линтера OpenAPI
```

## Диаграммы

Все диаграммы хранятся как код в `diagrams/*.puml` и отрендерены в SVG рядом с исходником. Чтобы перерисовать локально:

```bash
java -jar plantuml.jar -tsvg -charset UTF-8 diagrams/*.puml
```
